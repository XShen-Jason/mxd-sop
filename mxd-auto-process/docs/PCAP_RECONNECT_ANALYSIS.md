## 关键观察

### 1. 双连接并行
- Flow 46618在Flow 46622已经建立并运行1.6秒后出现
- 两个连接**同时活跃**
- 两个连接都接收相同的evt=18事件

### 2. Flow 46618特点
- **没有登录流程**（无op=0/op=6/op=7）
- 直接开始接收服务器事件
- 只发送ping，不发送业务操作
- 可能是客户端预先建立的备用连接或推送通道

### 3. 心跳模式
- op=19首次在18:59:55.285发送（登录后0.6秒）
- 之后不规律出现（不是固定20秒间隔）
- 在这个短暂的抓包中，心跳没有明显作用

### 4. 聊天操作
- op=12是聊天消息
- 出现在18:59:57.111, 18:59:58.133, 18:59:59.131等
- 没有对应的resp响应（可能是单向发送）

## 重连模式分析

❌ **该pcap不包含被踢重连的场景**

原因：
1. 两个连接同时活跃，不是顺序替换
2. 没有发现错误响应（rc ≠ 0）
3. 没有踢出事件（如"AccountLoginElsewhere"）
4. Flow 46618不是重连，而是第二个并行连接

##推测的实际重连场景

基于游戏协议常见模式，真正的重连应该是：

```
[原连接断开或收到踢出事件]
  ↓
[客户端检测到断连]
  ↓
[建立新TCP连接]
  ↓
[发送op=0登录] ← 使用保存的凭证
  ↓
[收到resp op=0 rc=0]
  ↓
[发送op=6选择角色] ← 使用保存的角色ID
  ↓
[收到resp op=6 rc=0]
  ↓
[发送op=7进入地图]
  ↓
[收到resp op=7 rc=0]
  ↓
[恢复到Ready状态，可以发送op=12聊天]
```

## 建议的实现方案

### 1. 断连检测
- TCP连接关闭
- 心跳超时（如果启用）
- 错误响应 rc ≠ 0
- 可能的踢出事件

### 2. 自动重连
- 保存登录凭证（账号+token）
- 保存角色信息（characterID + opaque）
- 保存地图ID
- 检测到断连后，自动执行完整登录流程

### 3. 心跳功能
**建议：禁用心跳**

理由：
- pcap中心跳不规律，作用不明确
- 增加网络开销
- 重连机制可以处理断连
- 用户明确要求禁用

## 操作建议

1. ✅ **禁用心跳**：将 `heartbeat.enabled` 改为 `false`
2. ✅ **实现重连**：基于设计文档实现自动重连功能
3. ⚠️ **需要新pcap**：如果需要分析真实的重连场景，需要包含"被踢→重连"的完整pcap
